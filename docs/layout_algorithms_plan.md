# Layout algorithm plan

## Goal

Add three selectable layout strategies for the PDF packet preview so users can compare how each one satisfies the packing rules and page count requirements.

## Shared constraints (all three modes)

All algorithms must respect the same hard rules:

1. If "Require each song to fit entirely on one page" is enabled, a song may still share a page with other songs, but it must not be split across pages.
2. Headers must not be visually broken by lyric content (no header row split by column/page transitions).
3. If "Maintain original list order" is enabled, the algorithm must preserve the incoming order while still honoring the one-page-per-song and section rules.
4. If "Maintain original list order" is disabled, reordering is allowed only within existing sections; section boundaries and section order must remain unchanged.

## Proposed algorithm modes

### 1. Compact Fill
- Best for minimizing wasted space.
- Greedily packs songs into the current column/page until the next song would overflow.
- Reorders songs within each section to keep the current page/column as full as possible.
- Expected outcome: usually the fewest wasted gaps, but may occasionally sacrifice a more balanced look.

### 2. Balanced Pages
- Best for minimizing the total number of pages while keeping each page visually balanced.
- Uses a search-based ordering that tries to avoid both under-filled columns and unnecessary page flips.
- Prefers orders that keep page/column usage relatively even while still respecting the one-page-per-song and section constraints.
- Expected outcome: strong page-count performance with a more even spread of content.

### 3. Stable Order
- Best for preserving the user’s intended song flow.
- Keeps the original order as much as possible, only moving songs when forced by the hard rules.
- Uses the minimum amount of reordering needed to avoid invalid breaks.
- Expected outcome: most predictable and least surprising, but not always the most compact.

## Implementation approach

### PDF engine
- Extend the PDF render entry point to accept a layout strategy parameter such as `layoutMethod`.
- Keep the existing layout preparation and rendering pipeline intact.
- Route each strategy through a small abstraction so the rendering logic remains shared.

Suggested contract:
- `layoutMethod: 'compact' | 'balanced' | 'stable'`
- Each strategy returns:
  - the final song order
  - page count estimate
  - basic stats (spill counts, whitespace, etc.)

### Optimizer layer
- Add three ordering functions in the PDF optimizer module:
  - `optimizeSongOrderCompact`
  - `optimizeSongOrderBalanced`
  - `optimizeSongOrderStable`
- Each should call the existing section-aware grouping logic first, then apply its own ordering behavior within each section.
- All three should share the same validation layer so the hard layout rules remain consistent.

### UI flow
- Add a compact selector in the preview/sidebar area with three buttons:
  - Compact Fill
  - Balanced Pages
  - Stable Order
- Each button should show:
  - the name of the method
  - the generated page count for that preview
- Clicking a button should:
  - regenerate the preview for that strategy
  - swap the preview pane to that version
  - keep the current packet settings and toggles intact

### State model
- Add a state value like `activeLayoutMethod` in the app state.
- Store preview results per method in memory, for example:
  - `previewResults.compact`
  - `previewResults.balanced`
  - `previewResults.stable`
- When a user switches methods, reuse the cached preview if available; otherwise generate it.

## Suggested UX

The preview header could look like this:
- Compact Fill — 18 pages
- Balanced Pages — 17 pages
- Stable Order — 18 pages

This makes the comparison immediate and helps users choose the layout that best fits their packet.

## Acceptance criteria

- The user can switch between three distinct layout methods from the UI.
- Each method respects the same layout constraints.
- The preview area updates to the selected method.
- Each button displays the page count generated by that method.
- The preview can be regenerated from the same packet state without losing the current settings.

## Suggested implementation order

1. Add the `layoutMethod` parameter to the PDF generation path.
2. Introduce the three optimizer strategies behind the same section-aware wrapper.
3. Add the preview selector UI and page-count labels.
4. Cache previews per layout method and switch them in the preview pane.
5. Add regression tests for each strategy’s constraint handling and page-count behavior.
